# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

WebGL2 recreation of the PlayStation 3 XMB background wave ("spline") and sparkle particles. The active implementation in `ps3xmbwave/` is driven by CPU-side pipelines reverse-engineered from the PS3's PPU and SPU code: `custom_render_plugin`'s lines and `spline.elf` for the wave, `particles.elf` and the plugin's emitter for the particles. `WAVE_REVERSE_ENGINEER.md`, `PARTICLES_REVERSE_ENGINEER.md` and `BACKGROUND_REVERSE_ENGINEER.md` are the sources of truth for that reverse engineering and document what is traced vs. still synthetic. Each is an index over topics split out under `docs/wave/`, `docs/particles/` and `docs/background/`; [Keeping the notes](#keeping-the-notes) says how to read them and add to them. `SPLINE_REVERSE_ENGINEER.md` is upstream's Ghidra reading of `spline.elf`, which `spline-reverse.js` ported until the wave pass replaced it with `wave-reverse.js`: it is not edited, and what the wave pass confirms or overturns in it goes into the wave notes.

## Commands

```bash
npm install          # only needed for the dev server / deploy tooling
npm run start        # serve the whole repo at http://localhost:8000
npm run dev          # same, opens a browser
npm run deploy       # upstream's gh-pages branch, which this fork's Pages does not serve
```

Entry points once served: `/ps3xmbwave/` (active), `/dds/` (gradient extraction tool), `/old-research/` (archived guesswork-era implementation).

The published site is `ps3xmbwave/` alone: `.github/workflows/pages.yml` uploads it as the root of https://faquino.github.io/PlayStation-3-XMB/ on every push to `main` that touches it (Settings → Pages takes its source from GitHub Actions).

Each of the three folders also has its own `docker-compose.yml` (nginx, read-only mount) if you want them served independently: `ps3xmbwave` → 9913, `dds` → 9919, `old-research` → 9828.

```bash
node tools/bench/particles.js --seconds 30 --runs 3 --seed 1
node tools/bench/wave.js --seconds 10 --every 2
```

The two benches. `particles.js` runs the particle simulation headless over the wave `wave-reverse.js` builds and prints its pool beside the same measurements read off the console — a savestate's pool, and its newborns pooled over the six savestates taken at rest; then, for each of two RSX frame captures, it plays the scene from the cold boot to the capture's lattice time, as `wave.js` plays its sources, and prints what it draws there beside what the capture's particle draw holds. Use it before and after touching the emitter or the wave. `wave.js` measures the wave `wave-reverse.js` builds — its band on screen, its depth, how fast it moves — beside the console's own wave, the meshes `spline.elf` wrote in the captures and savestates: for each of them it plays the XMB's start under the sets the console ran at that moment and runs the wave to the same lattice time, then pools the XMB at rest and the music, and lists the start capture by capture. The particle bench's pool runs night's set. Use it before and after touching the wave or the sets. Neither needs firmware — the console's column is recorded inside each. `tools/bench/pool-from-savestate.py` regenerates the particle column from a savestate, and pools the newborns of several. For the wave, `tools/bench/wave-frames.py` extracts the console's meshes into `re-work/wave-frames/` and `wave.js --console re-work/wave-frames` measures them again, and `wave.js --start` runs the lines from a start of one's own - the console's, read into `re-work/`, gives its wave frame by frame.

**There is no build step, no test suite, and no working lint setup.** Both tool scripts glob only the repo root: `npm run lint` (`eslint *.js`) matches no files and there is no eslint config, and `npm run format` (`prettier --write *.js *.html *.md`) only ever rewrites the root Markdown files (`README.md`, `SPLINE_REVERSE_ENGINEER.md`, this file) — it never reaches `ps3xmbwave/` or `dds/`. Don't rely on either as a verification gate. Verification is visual: serve the repo and look at the canvas, plus the browser console for shader compile/link errors (both renderers throw on failure). A caution when checking an edit that way: browsers hold on to the `.js` files hard here, and a forced reload does not always shift them — loading the page from `http://127.0.0.1:8000/` instead of `http://localhost:8000/` is a different origin with an empty cache, which does.

## Architecture

### Module system: browser globals, load-order dependent

`ps3xmbwave/` uses no bundler and no ES modules. Everything communicates through `window`: the data files (`*-settings.js`, `background-gradients-*.js`) are plain top-level `window.X = {...}` assignments, and every other file is an IIFE that exports onto it. `index.html` loads them with plain `<script>` tags in an order that matters:

1. `background-gradients-night.js`, then `background-gradients-day.js` — the day file's trailing IIFE **merges both** month tables into `window.BG_GRADIENT_PRESETS` and `window.BG_GRADIENT_PRESET_OPTIONS` (keys `MM_day` / `MM_night`, plus a `default` legacy entry and an `auto` one), and exports `window.bgGradientForDate`. Then `background-months.js`, the month textures' cubic fits (`window.BG_MONTH_FITS`), which `backdrop.js` draws the console's backdrop from on `auto`; the gradients are the other presets.
2. `spline-settings.js` — reads `BG_GRADIENT_PRESET_OPTIONS` **at load time** to build the preset dropdown, so it must come after both gradient files.
3. `scene-themes.js`, then `particles-settings.js` — same pattern: the settings file reads `PARTICLE_THEME_OPTIONS` at load time for its theme dropdown.
4. `settings-panels.js`, `wave-reverse.js`, `particles-reverse.js`, `xmb-input.js`, `backdrop.js`, `postprocess.js`, then `spline.js` / `particles.js`.

The global contract: `SPLINE_SETTINGS` + `SPLINE_SETTINGS_META` + `SPLINE_SETTINGS_LAYOUT`, `BG_GRADIENT_PRESETS` + `BG_GRADIENT_PRESET_OPTIONS` + `bgGradientForDate` + `BG_MONTH_FITS`, `PARTICLE_SETTINGS` + `PARTICLE_SETTINGS_META` + `PARTICLE_SETTINGS_LAYOUT`, `PARTICLE_THEMES` + `WAVE_THEMES` + `PARTICLE_THEME_OPTIONS` + `PARTICLE_THEME_KEYS` + `WAVE_THEME_KEYS` + `applySceneThemes` + `xmbSceneDate` + `xmbBackdropMoment` + `xmbSceneFade` + `xmbSceneGamma`, `createSettingsPanel`, `PS3WaveReverse`, `PS3ParticlesReverse`, `PS3Backdrop`, `PS3PostProcess`, `createXmbInput`, `createSplineLayer`, `createParticlesLayer` + `PS3Iridescence`. `dds/` is the exception — it uses real ES modules (`<script type="module">`).

### Frame loop and layering

`index.html` owns the canvas, the WebGL2 context, DPR-aware resize, the `H` key and `?ui=off` that put the controls and the notice at the bottom away (a `ui-off` class on `<body>`), and the `requestAnimationFrame` loop. The page opens with the XMB's start: `index.html` sets `sequence` to `coldboot` once the panel is made, so the setting's default, and what the benches run, stays `none`. It advances one clock, has `applySceneThemes` write the scene's sets into both layers' settings, and calls `splineLayer.render(t, moment, sequence, fade, gamma)` - `moment` what the scene last handed the backdrop, `xmbBackdropMoment`: its clock's moment on each tick, a second apart, which Theme Settings' Colour stops and the XMB's start, a content's boot and the music hold, or 10:00 as the XMB's start begins, with how long it takes to ease in; `sequence` the boot sequence playing, whose XMB start resets the wave's lines; `fade` the scene's fade as `xmbSceneFade` last sent it; and `gamma` its `_Gamma`, `xmbSceneGamma`'s - then `particlesLayer.render(t, dt, fade, gamma)`: the particles are emitted from the wave just drawn, so they share its clock, and the fade and `_Gamma` go to both layers, as the console's scene sends them to both. It hands the spline layer's `surface` (its settings and the wave's mesh) and the input adapter to the particle layer. Per frame:

- the backdrop (`backdrop.js`), into its 64 × 32 buffer: on `auto`, a copy of that buffer and over it `back_colours0` over the month fits or `back_colours1`, re-authored, blended by `_Alpha` (`SRC_ALPHA / ONE_MINUS_SRC_ALPHA`); otherwise a preset's gradient, blending off
- wave mesh (128×128, triangle strips with primitive restart, the console's own layout), into a buffer of its own, its light in `_Encode`'s red and green — additive `ONE / ONE`
- the passes after the wave (`postprocess.js`): the composite of the two with `BACKGROUND.mnu`'s colours times the scene's fade, `HDR.mnu`'s tone curve and noise into an 8-bit screen, the glare drawn out of it in half-float targets, and the sum into the canvas
- particles (instanced quads, two passes: lit flakes, then glare sprites) — additive `ONE / ONE`, over that

Depth testing is never enabled. The wave's vertices arrive in clip space, already projected by the XMB's camera (eye at (0, 0, 2) looking down −z, 53° vertical field of view), and its vertex shader passes them through, as the console's does. The particles use the same camera, and the emitter takes the wave's vertices back into the world by undoing it.

### The reverse-engineered wave

`wave-reverse.js` exports `PS3WaveReverse.createWave()`. Each frame `spline.js` calls `update(settings, dtSec, aspect)`, which builds the wave the way the console does and writes it into `mesh`: 16384 records of 8 floats, position in clip space then normal, the layout `spline.elf` writes. `texcoords` and `indices` are the mesh's static parts. The stages, in order (`WAVE_REVERSE_ENGINEER.md` indexes how each was traced and checked):

`step` (`custom_render_plugin`'s 19 × 19 lines at 60 Hz: springs, noise, integration, anchored ends) → `receive` (the grid the task receives: the points interpolated by the accumulator, then shaped by `FFD PARAM 1`) → `buildLattice` (`ffd_shader1.fpo`'s formula at ten times the clock the frame began with, scaled and laid out 11 × 7 × 7; as the clock goes back to 0, `crossFrame` crosses it over from the old time for 200 frames, as `ffd_alpha_blend.fpo` does) → `deform` (`spline.elf`'s tricubic free-form deformation) → `buildMatrix` / `transform` (projection, view and the wave's model matrix) → `evaluateSurface` (the bicubic B-spline surface, 8 × 8 samples per span, with normals).

Its constants come from traced addresses, each commented with it, and are not free parameters; reconcile with the wave notes before changing them. Its parameters are `LINE1.mnu`'s, which the scene's sets move as they move the particles' (`scene-themes.js`), and `reset()` puts the lines back to their start, as the XMB's start does. What is modelled is marked: the lines' start (the console's is a baked snapshot in its module, which is firmware data, so the module makes its own by running the lines), at most four steps a frame, the crossing over's frames at 60 a second, and the deformation's exact division. `window.__PS3_WAVE_STATE` holds its counters for console inspection.

`spline.js` draws the mesh with `lines1.vpo` and `lines1.fpo` re-authored in GLSL, blending additively, and writes the light as `_Encode` holds it, a fine part in red and a coarse one in green. Its three textures are generated at start-up: `_Stripes` and `_Encode` as the console's lines renderer makes them, to the byte, and `_FresLUT` from a fit to the firmware's file.

### The backdrop

`backdrop.js` exports `PS3Backdrop.create(gl)` and `PS3Backdrop.uniforms(settings, date, shader)`. On `auto` it draws the console's backdrop programs, as `COLOUR SHADER` picks: `back_colours0.fpo` over the month textures' cubic fits, which `tools/re/month-fits.py` writes into `background-months.js` from the user's own firmware, or `back_colours1.fpo`, the music's - both re-authored and checked against RPCS3's decompilation to float precision. Each is eased in from a copy of the buffer, as the console's are: a moment handed over (with the length of its ease) or a change of program (2 s) starts an ease, whose first frame copies the buffer aside, and `_Alpha` is the smoothstep of the frame time since. `draw(settings, moment, dtSec, target)` takes the buffer `postprocess.js` hands it, and `uniforms` works out the clocks from the moment and `BACKGROUND.mnu`'s settings as the scene does (`0x52ad8`). The other presets draw their gradient as it is. Modelled: the textures as fits, and the page's first frame, eased into from black rather than from midnight in January. `BACKGROUND_REVERSE_ENGINEER.md` has how each was read.

### The passes after the wave

`postprocess.js` exports `PS3PostProcess.create(gl)` and `PS3PostProcess.uniforms(settings, fade, gamma)`. `spline.js` draws the backdrop into its `drawBackdrop` target, which it hands the drawer, and the wave into its `drawWave` one, then calls `present(settings, width, height, fade, gamma)`, which runs the console's passes between the wave and the particles, re-authored from the decompiled programs: `LinesController` (the backdrop times the gradient of `BACKGROUND.mnu`'s colours 1 and 2, the decoded light times that of 3 and 4, each colour times the renderer's fade, which `spline.js` runs as the console's renderer does, through the preexpose tables - `HDR.mnu`'s tone curve at `EXPOSURE` times `_Gamma`, read half a texel short, which takes 1/16 off the light - and the glare's mask, with the noise, into an 8-bit screen), `GlareSourcePre`, the six levels, `Gaussian`, `AccGlare` and `ToneApplyDisplay`, into the canvas. `uniforms` works out what the programs get from the settings, as the console's HDR renderer does and the captures show; the tables' layout, the encoding's constants and the levels' sizes are the firmware's, commented, and not free parameters. The noise is drawn afresh every frame, as that renderer draws it, from its own counter and hash. Modelled: the wave's buffer read bilinearly where the console's texture unit applies a convolution, the glare's levels added in one pass, and its textures clamped to their edge, as RPCS3 runs their CLAMP. Without `EXT_color_buffer_float` the glare is left out. `docs/wave/postprocess.md` has how each was read.

### The reverse-engineered particle system

`particles-reverse.js` exports `PS3ParticlesReverse.createSystem()`, and `particles.js` calls its `update(...)` once per frame before drawing. The file has two halves, marked in the code:

- **Verified:** `runTask` is the SPU update task of `particles.elf`, steps 1–8 of `docs/particles/spu-task.md` in order: flow grid sample, noise from three generators reseeded every frame, field rotation, vec4 integration (life in `position.w`, aging rate in `velocity.w`), quaternion spin, death back to the free list, vertex record. Its constants (`FREE = -666`, `LIFE_END`, `NOISE_SEEDS`, `SPIN_FREQS`, `LIFE_MIN`/`LIFE_MAX`, `CAMERA`, `GRID_SCALE`/`GRID_ORIGIN`, `FIELD_CENTRE`) and the 2304-byte block `createParams` lays out were read out of the firmware, RPCS3 savestates and frame captures (`tools/re/readblock.py`). The PPU side of `custom_render_plugin` is ported as far as it is traced: `buildParams` (the block, the wind and the noise's spring), `decayGrid`/`iconWind` (the flow grid), `pickVertices`/`sweep`/`emitAt` drawing from `createQglRandom` and reading the wave's mesh through `waveToWorld` (the emitter), `readSensor`/`dpad`/`detectShake` (the controller), `applySpe` (`PARTICLES_SPE.mnu`, under `videoOutput` and `whatsNewBoard`) and `colorFade` (`_Color`); the icons' layout (`ICON_*`, `ITEM_*`) is measured in the captures. None of them are free parameters; reconcile with the notes before changing them.
- **Modelled:** two things the XMB does outside the scene's code: how the icons move between their places (`moveIcons`) and when a held direction repeats (`FIRST_REPEAT_FRAMES`, `REPEAT_FRAMES`). `docs/particles/implementation.md` records how.

`particles-reverse.js` is the largest file in the repo, about 50 KB: find the function a task needs and read that range rather than the whole file.

The simulation steps at a fixed 60 Hz, because the task's semantics are per frame (life advances by the aging rate once per step). It runs at most 4 steps per frame, pre-warms 300 steps on the first frame so the scene starts full, and skips frames while the canvas is empty. Input gathered between steps is held until a step consumes it. `window.__PS3_PARTICLES_STATE` holds its counters for console inspection.

`particles.js` draws the system in the two passes the XMB uses, `particles_quads` then `particles_second`, re-authored in GLSL from the decompiled programs, with the parameters the system ran on (`system.effective`: the settings with `PARTICLES_SPE.mnu` applied) and the `_Color` its fade has reached (`system.colorFade`). They are rewritten, not copied — firmware shaders never go in the repo. The iridescent texture is built from `iridescentPalette`, by default 16 colours fitted to the firmware one, and built again whenever the setting holds a new palette; `PS3Iridescence` builds it, and the preview of it that `index.html` hands the panel.

`xmb-input.js` stands in for the controller, so the web page has something to react to; what it hands over is the console's own input:

- the arrow keys send D-pad steps in the XMB's four directions, and the newest key down is reported as held — the simulation repeats it 30 of its frames after its step, the page's choice, then every 8, as the captures imply; the browser's own key repeat is not used. Up and down turn the field as left and right do (`verticalSteps`, the page's choice: the console's `dpad scale y` of 0 has them only scroll its items), and a horizontal and a vertical arrow held together turn it about the diagonal, no faster than one direction — `docs/particles/input.md` has the page's input;
- dragging with the mouse moves a virtual Sixaxis, reported as the four sensors the PPU reads (the accelerometer's x, y and z, and the gyro) in its own units.

It also hands over where the pointer is, which the console has no counterpart for: the system writes its motion into the flow grid through the icons' own writer, in both directions and times `pointerWind`, so it pushes the particles it passes over as a moving icon would.

The system polls it once per frame and hands the steps to the simulation one per step, as the XMB sends them.

The simulation files run under Node for headless checks with `globalThis.window = globalThis` and an indirect `eval` of each file in load order. Don't use a `vm` context: global lookups there make it about 30× slower. `tools/bench/particles.js` is that harness: it compares the pool against the console's, slot for slot in the task's own record layout, which is why `createSystem` takes an optional `seed` and the system exposes `pool`, `stride` and `free`. `tools/bench/wave.js` loads the same files to measure the wave.

### Settings and UI

`settings-panels.js` builds one panel, in tabs - Scene, Input, Backdrop, Wave, Post, Particles - over both settings objects, by **introspecting them**: every finite numeric key becomes a slider, keys whose meta says `type: 'select'` become a dropdown, or a pair of radio buttons when they have just two options, which write the option's own value, a key whose meta says `type: 'palette'` (an array of `0xRRGGBB` colours) becomes a strip of swatches, each opening the browser's colour picker, with + to add a colour between the last and the first and − to take the last away under its Reset, within the meta's `min` and `max`, beside the preview its source's `previews` hands for it, keys missing from the meta map fall back to an inferred ±2× range, and a meta's `help` becomes the label's tooltip. Each settings file's `*_SETTINGS_LAYOUT` (`{ tab, section, keys }` entries) says which tab and which titled section each key goes in, in order; a key it leaves out lands in an Other section of its source's `defaultTab`. A meta's `hidden`, a string saying why, keeps the key off the panel but in the settings, for what the code still reads: closed questions (`whatsNewBoard`, `iconEaseSec`), a constant (`flowStrength`), firmware parameters with no visible effect (`falloff`, `endX`, `spacing`, `thinness`), and the backdrop's presets of before it was read (`gradientPreset` and the RGB preset's knobs). `createSettingsPanel` takes each object as a source, `{ settings, meta, layout, lockable, defaultTab, previews }` by name (`particles`, `wave`); `previews`, by key, are functions of a palette that return `{ width, height, data }` for its preview, as `ImageData` holds them. It snapshots each object at creation time to implement per-row Reset, marks the rows whose value was changed from the panel (in amber, with their Reset enabled, a count in the header and on their tab and, for the settings a source's `lockable` lists, a padlock that locks the value; the returned `locked`, a Set by source, holds them) and the ones something else set off their defaults (in its colour: lilac for the theme, teal for a sequence, pink for the music), and mutates the live objects in place — renderers read `settings.*` fresh on every frame, so no re-initialization or event wiring is needed. A palette's array is the exception: the snapshots are shallow copies, which share it, so the panel only ever replaces it with a new one, never changes it in place, and `particles.js` builds its texture again when the array is a new one; anything else that writes a palette has to do the same. The tab last chosen is kept in `localStorage` (`ps3xmb.settingsTab`).

Consequences when adding a knob:

- A new numeric key in `SPLINE_SETTINGS` / `PARTICLE_SETTINGS` gets a slider automatically; add a matching `*_SETTINGS_META` entry or the range will be nonsense, and put it in its `*_SETTINGS_LAYOUT` section, or it lands in Other.
- Give that entry a `help`, which the panel shows as the label's tooltip: what the knob does, then, after a `\n`, where it comes from — the `.mnu` file and parameter name for a firmware one (`PARTICLES.mnu: emit vel min`), or where it acts for the others.
- Wiring it to a shader needs three edits in the renderer: the `uniform` declaration in the GLSL string, the location lookup (the `waveU` map in `spline.js`, the `program(...)` lists in `postprocess.js`, the `UNIFORMS` list in `particles.js`), and the `gl.uniform*` call (`render` in `spline.js`, `present` in `postprocess.js`, `setUniforms` in `particles.js`).
- The wave's other knobs need no shader change — `wave-reverse.js` reads them as it builds the mesh.

`PARTICLE_SETTINGS` keys are the `.mnu` parameter names in camelCase (`PARTICLES.mnu`, then `PARTICLES_UI.mnu`), with the firmware values as defaults — keep that mapping so the settings can be checked against the firmware. Then comes `iridescentPalette`, which is no `.mnu` parameter but `proc_iridescent.tga`'s colours, as fitted. `SPLINE_SETTINGS` does the same for `LINE1.mnu`, then `HDR.mnu` and `BACKGROUND.mnu`, after the backdrop's keys; `BACKGROUND.mnu`'s colours, whose names start with their number (`1 RED`), are `colour1Red` to `colour4Blue`, and its other parameters follow, with the code's defaults where the base file leaves them out. Knobs of the modelled side and the mouse adapter go in the last group, with `videoOutput`, `whatsNewBoard`, `musicPlayback`, `themeBrightness`, `themeColor` and `xmbBackground`, the console's state the scene is drawn under. The order of the objects is the firmware's; the panel's order is the layouts'.

`scene-themes.js` holds the firmware's per-theme parameter sets as differences from those defaults, `PARTICLES.mnu`'s on the particles' side and `LINE1.mnu`'s, `HDR.mnu`'s and `BACKGROUND.mnu`'s on the wave's, and `applySceneThemes(scene, layers, date)` writes one of them (or, on `'auto'`, the day's blend of two) into each layer's live settings - `layers` names `particles` and `wave`, each with its settings and the Set of names locked on it, and `scene` is the particle settings, which hold the scene's state below. It also plays the boot sequence `sequence` names on top of the theme - the XMB's start, a game's launch or another content's, with the timings read out of the scene's `.rco`, the XMB's start ending on the scene clock's first tick after ShowGUI as the console's does - and writes `sequence` back as one hands over to the next or ends; the particle system rebuilds its pool, empty, when the XMB's start begins. The music (`musicPlayback`) takes the theme's place while it holds the scene's clock, coming in and going out as the scene's code times it, and Theme Settings' Colour (`themeColor`) stops that clock, at the moment `xmbSceneDate` returns; `xmbBackdropMoment`, which `index.html` hands the backdrop, is that moment as the clock's ticks hand it over, a second apart, none while the XMB's start, a content's boot or the music holds the clock, or 10:00 of the day as the XMB's start begins. A whole-number parameter, `COLOUR SHADER`, goes in at once rather than blending, and `DAYSPREAD`, whose default lies below its range, is held to it as the scene holds its parameters (`RANGES`), so the sets that leave it out read it as 1. `xmbSceneFade` is the scene's event 0 as the XMB sends it and the scene's handler turns it into a fade - Theme Settings' Brightness (`themeBrightness`) or the background given away (`xmbBackground`, over `backgroundFadeMs`) - which `index.html` hands both layers, the particles' `_Color` and the wave's renderer each running it. `xmbSceneGamma` is `_Gamma`, the colour `paf` draws the interface with, which `vsh.elf` sets by the video output: 0.8 on SD (`videoOutput`), 1 above, handed to both layers too. It writes only when the theme or the blend moves, and then only the settings it moves, so a value set by hand survives until the theme moves that very setting; one in its `keep` Set (the panel's `locked`) survives that too, and catches up with the theme as soon as Reset puts back what was last written into it. `PARTICLE_THEME_KEYS` and `WAVE_THEME_KEYS` list the settings it can write, which the panel makes `lockable`. `index.html` calls it every frame and, for each layer it reports a write on, calls the panel's `refresh(layer, writer)`, which `createSettingsPanel` returns, naming the writer (`'sequence'` while one plays, `'music'` while the music holds the clock, `'theme'` otherwise) — the controls of the settings it wrote catch up, and the values they land on become what Reset returns to, in the writer's colour where they differ from the defaults, while a setting changed from the panel and not written since keeps its amber mark and its Reset value. Anything else that writes settings from outside the panel has to do the same.

### `native/` — Rust port

Nagare: a Cargo crate (`cargo run --release` from `native/`; the crate and executable are `nagare` (nagare.exe), the config folder `Nagare`, renamed from `ps3xmb` on first run) that ports `ps3xmbwave/` file for file to Rust on OpenGL 3.3 (glutin, winit), with an egui settings panel; the panel's top names the product and credits faquino's and linkev's repositories. The product's name is Nagare; PS3, PlayStation and XMB name only what it recreates, never the product. Vulkan is the default renderer (`src/vk/`, through wgpu 30 - Metal on macOS), OpenGL the original one, and a third, Software, is wgpu on the system's software rasteriser (WARP on Windows); `--renderer` or the Resources tab picks one, switched live by making the window again, and where one cannot start or fails while drawing the next takes over (Vulkan, OpenGL, software; `NAGARE_FAIL` forces failures to test this); under the software renderer `softwareLite` leaves the heavier features out, and `renderScale` draws the scene smaller under any. Vulkan it runs the GL renderers' very GLSL, rewritten by `vk/glsl.rs` for naga (a std140 block, split samplers, locations, y turned over and depth remapped, so every image lies in memory as GL's does), with the same uniforms from the same functions, and draws to within a few pixels' single step of OpenGL; `vk/wave_gpu.rs` runs spline.elf (the deformation and the surface) as compute passes, in f64 where the GPU has it, and the particles' emitter then works out only the vertices it picks (`Wave::vertex`). The simulations live in `src/sim.rs`, apart from either renderer. OpenGL's output must not change: `--test` shots before and after any change to shared code are compared byte for byte. On Windows it starts behind the desktop icons as a wallpaper (`src/wallpaper.rs`, which also reads the mouse off the desktop; `--window` for a window), with a tray icon (`src/tray.rs`, put on the taskbar through Explorer's `IsPromoted` on each copy's first start only, then left where the user puts it), Ctrl+Alt+Shift+W to toggle it, and poking the desktop - clicking it `pokesToOpen` times in quick succession, each poke bouncing the camera, which moves only the drawing (`wave::set_dolly`: the wave's clip coordinates and the particles' view), never the simulations - opening the settings in a window of their own (`src/settings_window.rs`, whose backdrop is the scene's blur or one of Windows' materials); right-clicking for the logo is an option (`logoOnRightClick`). `native/README.md` maps each module to the page file it ports and lists the options. The JS stays the source of truth: a change to the wave, the particles, the passes or the scene's sets is made there first, then carried into the matching Rust module with its constants and address comments. `src/months.rs` is generated from `background-months.js`. Some of it is the app's own, with no page counterpart: `src/perf.rs` (the perf overlay, `--perf-overlay 1-3`, nothing of it run while it is off; the panel's maru-time adds `src/steamboat.rs`, Nagare-maru, a cartoon steamboat riding what the music's listening hears), `src/auto_exposure.rs` (AE, a push or pull on `EXPOSURE` run wholly on the GPU, metering the final frame or the composite before the glare - nothing is read back in the frame, since any read back waits a whole refresh on NVIDIA's threaded driver), the enhancements in `src/postprocess.rs` (the exponential bloom, the default glare; a multiplier on the console glare's radii; sensor noise, or AlexaGrain, an ALEXA's film grain after the Nuke gizmo, baked into a tile, on by default; highlight desaturation; `src/antialias.rs`'s FXAA (both renderers) and supersampling (Vulkan); `src/sharpen.rs`'s sharpening, AMD's CAS re-authored, over the finished frame; `src/maru.rs`'s maru-chan, the steamboat as a 3D boat sailing the wave now and then (the Maru-time tab), in the 2D boat's proportions, frosted refracting glass facing the eye, drawn by both renderers from one CPU-sorted triangle list after the particles, supersampled and motion-blurred in a tile of its own, and optionally lit by a small eased map of the frame's light; `src/disco.rs`'s disco ball, lowered near the top right after minutes of heavy bass under the music, its mirror tiles drawn per pixel (no mesh) and its beams through the haze, spots and glints worked out on the CPU from the same tiles, its lights going with the beat; `src/warning.rs`'s photosensitive epilepsy warning, as the console shows it as it starts, before the XMB's start (which then plays again) or over the blurred scene after it, drawn by the panel's egui pass; `src/intro.rs`'s first start - a benchmark, run unseen under a screen of the console's dialogs whenever the display drivers are new to `src/machine.rs`'s `machine.json`, which chooses the frame cap's Auto (60, or 30), then the warning and a card after the console's advertisements; `src/scene.rs`'s Season Pass, a tour of the months' backdrops in place of the clock's month; the tonemappers - with each off, the console's passes run unaltered), the music's (`src/media.rs`'s autoMusic, on by default, `musicClockColour` in `src/scene.rs`, and `src/audio.rs`, which while the music holds the scene listens to the output through WASAPI's loopback and moves the wave's brightness with how loud it has been for a while, the bass raised, and bounces the camera on the beat - found in four bands' onsets, the bass weighted most, by an autocorrelation summed over the period's multiples and a phase-locked beat, and gated by the loudness or the drums' hits at the moment; the bass's pitch, read by YIN on the low band taken down to 1.5 kHz, flickers the brightness and shakes the camera at its rate, folded under the frame rate (the shake under the rate the sub-frames are drawn at), and its kicks can bop it, all three opening over a warm-up once a sure beat is heard and closing after minutes without music; what the pokes and the music move is drawn in sub-frames, up to 240 a second, averaged as motion blur (`wave::subframes`, the wave summed in a float buffer), only on frames where something moves - both, like the poke, only in the drawing, through `wave.rs`'s gain and dolly), `src/config.rs` (the autosaved config: the panel's changed values, locks and scene state, in the platform's config folder, written by a thread of the lowest priority; `--config` takes another; renamed settings are read under their old names through `settings.rs`'s `RENAMED`), `src/blur.rs` (the settings' blurred background, the Panel tab), `src/neighbour.rs` (other programs' conditions - a window maximized or full screen, a listed process, the battery, the GPU's memory - which the Resources tab turns into limiting, pausing or stopping, a stop dropping the GL context to free the GPU's memory), `src/autostart.rs` (Start with Windows, offered only to a copy installed by `installer.ps1`'s Inno Setup installer, `installer/nagare.iss`, per user into `%LOCALAPPDATA%\Programs\Nagare`; `installer/INSTALLER.md` says how to build it, `-Install` installs it silently, and its look is `installer/theme`, which `nagare-customize` writes), `src/cpu.rs` (where the threads run - E-cores, one cache cluster, EcoQoS, priority - each thread's CPU, and `lowest_priority` for helpers whose work can wait) and the controls at the panel's top. Their settings are `NativeSettings` in `src/settings.rs`, a third settings object beside the wave's and the particles' that the scene's sets never write; enhancements go there, behind a setting whose default keeps the console's look (the bloom and the Gran Turismo tonemapper excepted, at the user's request), and the panel shows them first on their tab under Enhancements, titled [Enhancement], above the Console-original knobs. Verification is the same as the page's: run it and look, with `--window --perf-overlay 2` for the costs. `--test` makes a run repeatable - defaults, no config, a seeded emitter and a fixed clock, so a frame is the same to the byte every run - with `--shot SEC=FILE` to save frames for comparing renders, `--report FILE` for each stage's and thread's costs, `--set KEY=VALUE` for variants and `--set-at SEC:KEY=VALUE` to change one mid-run; measure release builds paced at 60 fps (debug builds' egui error checks spin on NVIDIA's driver). `pgo.ps1` builds with profile-guided optimisation from such runs - about twenty minutes, so only for a release or a performance comparison; a plain `cargo build --release` otherwise, which the release profile keeps quick with thin LTO over 16 codegen units (`pgo.ps1` sets fat LTO and one unit for itself). `pgo.ps1 -Save` keeps the profile in `native/pgo/`, and `-Use` builds from it without training: the GitHub workflows `.github/workflows/native-ci.yml` (clippy on three targets, tests, a plain build) and `native-release.yml` (a `v*` tag: `-Use`, the installer, SignPath signing once configured, a draft release whose body is `.github/release-notes.md` with the version filled into its download links) build under the compiler `native/rust-toolchain.toml` pins, which a profile has to match. The root `README.md` is Nagare's; upstream's is kept as `README.upstream.md`. Two more binaries: `nagare-watchdog` (`src/bin/watchdog.rs`), which the app starts and which starts the app again after a crash, and `nagare-customize` (`src/bin/customize/`), the customizer: its App icon tab designs the logo and renders `assets/logo` - the PNGs `src/logo.rs` takes in and the `nagare.ico` `build.rs` puts into the executables - its Installer icon tab the installer's glass box (`setup.ico`), and its Installer tab the setup wizard's look and pictures (`installer/theme`, which `nagare.iss` takes in), and it builds and installs the installer. `cargo clippy` is clean (also for `--target x86_64-unknown-linux-gnu` and `aarch64-apple-darwin`), and `native/target/` is ignored.

### `tools/re/` — reverse-engineering tooling

Python tools (standard library only, except `ppu_prx.py`, which needs capstone) that read the user's own PS3 firmware (for example an RPCS3 install): a `.qrc` extractor, an SPU disassembler, a matcher that uses RPCS3's SPU cache to show which code actually ran, a Cg binary (`.vpo`/`.fpo`) inspector that recovers uniform values from RPCS3's shader cache and maps the constants of RPCS3's decompiled fragment programs back to uniforms, a reader for RPCS3 RSX frame captures (vertex constants and vertex buffers per draw call, and a frame's draws with their programs, targets, textures and live uniforms), a PPU module loader and disassembler, a reader of RPCS3 savestates' memory by the PS3's own addresses (`savestate.py`), and the writer of the month textures' fits (`month-fits.py`), whose output, fitted data, is committed. `tools/re/README.md` has the workflow. They write into `re-work/`, which is gitignored — **firmware files (ELFs, `.qrc` contents, textures, decompiled shaders) must never be committed**. `WAVE_REVERSE_ENGINEER.md` (an index into `docs/wave/`), `PARTICLES_REVERSE_ENGINEER.md` (an index into `docs/particles/`) and `BACKGROUND_REVERSE_ENGINEER.md` (an index into `docs/background/`) are what the tools have found about the wave, the particle system and the backdrop.

### `dds/` — gradient extraction tool

Standalone browser tool (ES modules) used to produce the month gradient presets, which the dropdown offers beside `auto`. `dds-reader.js` parses DDS (DXT1/3/5 and masked uncompressed formats) in pure JS; `gradient-fit.js` brute-forces the gradient angle and runs per-channel linear regression to fit a 2D linear gradient, reporting RMSE; `export-code.js` emits JS preset source. The exported record shape (`width`/`height`/`rmse` included) does not match what `background-gradients-*.js` actually stores (`angleDeg`, `colorStart`, `colorEnd`), so exported output is trimmed by hand when pasted in. The `.dds` source files are firmware assets and are not in the repo.

## Conventions

- `'use strict'` at the top of every `ps3xmbwave/` file, with the logic files wrapped in an IIFE; two-space indent; single quotes in `ps3xmbwave/` (double quotes in `dds/`).
- Every `ps3xmbwave/` file except the two `background-gradients-*.js` data tables opens with a two-line header comment stating what it produces and which files consume it — keep this up to date when dependencies shift.
- Settings files are declarative only: no runtime logic in `*-settings.js`.
- `old-research/` is a frozen archive (uses regl + stats.js). Don't refactor it or import from it; it exists for reference only.

## Keeping the notes

The wave's, the particles' and the backdrop's notes are built the same way: an index at the root (`WAVE_REVERSE_ENGINEER.md`, `PARTICLES_REVERSE_ENGINEER.md`, `BACKGROUND_REVERSE_ENGINEER.md`) with *Topics*, *Status* and *Still missing*, over topic files in `docs/wave/`, `docs/particles/` or `docs/background/`, one of which, `history.md`, holds what everyday work does not need. These rules apply to all three; each index's own *Keeping these notes* adds what is particular to it.

- **Read narrowly.** The index first, then the topics the task needs. To find an address, a function or a parameter, search for it (`grep -rn 0x2dde4 docs/`) rather than reading every file. `history.md` is for reopening a closed question.
- **Write what is known now.** A finding goes into its topic, and a reading it overturns is corrected where it stands, not answered by a new section further down. How it was found (which captures, at what time, the leads that failed) goes in the commit message, and in `history.md` only if it is worth keeping beside the notes.
- **Close the loop in the index.** When a question opens or closes, update the index's *Status* and *Still missing* in the same commit.
- **Retire what is superseded.** A reading that no longer holds leaves its topic; git keeps it. A dead end that would save someone the search gets a line under *Ruled out* in `history.md`.
- **Keep the scene's shared ground in one place.** The camera, the parameter sets, the day cycle and the scene's events belong to the whole scene, and the particle notes describe them. What any pass finds about them goes there; the wave's and the backdrop's notes link to it and keep only what concerns them alone.
- **Mind the size.** Keep each index under 8 KB and each topic under 15 KB. A topic that outgrows it is split by subject, and the new file goes into the index's *Topics*.
- **Don't restate the code.** Constants and their addresses are commented in `ps3xmbwave/`, and a bench's figures live only in its notes' `implementation.md`, replaced when it runs again rather than added to.
- **Methods go with the tools.** How to read savestates and captures, and how to get RPCS3 where a reading needs it, is in `tools/re/README.md`.
